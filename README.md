# bas_runtime
Runtime обработки изображений для платы luckfox-pico-pro-max

## Конфигурация

Настройки рантайма читаются из `config.ini`, настройки модели — из `model.ini`, настройки
внешнего скрипта — из `hook.ini`; все три лежат рядом с бинарником и ставятся вместе с ним.
Ключ можно не указывать — отсутствующий ключ и значение, которое не удалось разобрать,
заменяются значением по умолчанию из кода. Сами файлы должны существовать и быть
синтаксически корректными, иначе программа сообщает об ошибке и не запускается.

`config.ini` — камера, кодирование и RTSP. `model.ini` — тип модели, файл `.rknn`, размер
его входа, пути до файлов с названиями классов и якорями, а также ручки детекции
(пороги и лимит рамок). Реализация разбора выходов выбирается ключом `type`; под YOLOv5
это `br_model_yolo`. `hook.ini` — внешний скрипт: включение, режим работы, файл
пользовательского скрипта и бюджет ожидания.

Состав ключей и значения по умолчанию описаны в [config.ini](./config.ini),
[model.ini](./model.ini) и [hook.ini](./hook.ini).

## Внешний скрипт (хук)

Рантайм может отдавать кадр внешнему python-скрипту: скрипт рисует поверх кадра что хочет,
а размеченный кадр уходит в RTSP. Своей отрисовки в рантайме нет — рамки и подписи рисует
только скрипт. Пока хук выключен или скрипт не ответил, в поток идут кадры с камеры.

Хук — это два файла, оба ставятся рядом с бинарником:

- `hook_main.py` — обвязка рантайма: разделяемая память, ожидание кадров. Рантайм запускает
  ее сам и передает ей путь до пользовательского скрипта; трогать этот файл не нужно.
  Бинарник и обвязка видят разделяемую память по одной раскладке, поэтому обновлять их надо
  только вместе: со старым `hook_main.py` пары «бинарник + обвязка» не бывает.
- пользовательский скрипт — то, что указывается ключом `script` в `hook.ini` (по умолчанию
  пример [hook_user.py](./hook_user.py)). От него нужна одна функция:

```python
def draw(frame, detections):
    # frame      - numpy (height, width, 3) uint8, порядок каналов RGB: рисуй прямо в него
    # detections - список объектов: left, top, right, bottom (пиксели кадра), prop (0..1), name
```

Что рисовать поверх кадра — дело скрипта: рантайм и обвязка в отрисовку не лезут. В примере
скрипт считает покадровые векторы движения оптическим потоком (детекции ему для этого не нужны)
и рисует fps.

Как это устроено:

- скрипт — отдельный процесс классического `python3`, поднимается один раз и живет все время
  работы рантайма; кадр и боксы детекции он получает через разделяемую память (POSIX-объект,
  имя которого рантайм снимает сразу после открытия, так что в системе за ним ничего не
  остается), туда же пишет ответ — ни сокета, ни файлов, ни сигналов. Боксы уезжают с каждым
  кадром — последние посчитанные: прогон модели идет своим темпом (это видно по `det` в строке
  `[fps]`), а скрипт все равно получает рамки каждый кадр, пусть и повторенные;
- кадр едет без копий: RGA кладет копию кадра в отдельный буфер сразу в формате потока (RGB888),
  дескриптор буфера уезжает скрипту в разделяемой памяти, скрипт делает по нему `mmap` и рисует
  прямо в буфере. Формат тот же, что уходит в VENC, поэтому возврат размеченного кадра в поток —
  это копия без конвертаций: в тот же буфер скрипт сразу получит следующий кадр, так что отдать
  его в VENC напрямую нельзя. Цвета в кадре скрипта задаются в порядке RGB;
- пока скрипт работает, кадр ему не отдается: рантайм продолжает отправлять в поток текущие
  кадры с камеры, а размеченный кадр забирает, как только скрипт ответит. Значит, в `async`
  размеченные кадры идут вперемешку с чистыми: пока скрипт думает над кадром, в поток уходит
  кадр без разметки. Если скрипт не укладывается в кадр потока (33 мс на 30 fps), разметка
  мелькает — это цена режима, который не ждет;
- два режима. `sync` — конвеер ждет скрипт, но не дольше `timeout_ms`: разметка того же кадра,
  а частота кадров режется на время работы скрипта; не дождались — в поток уходит кадр с камеры.
  `async` — ждать не ждем: кадр скрипта уходит в поток со сдвигом в один кадр, частота кадров
  не падает;
- правка файла скрипта подхватывается на горячую: рантайм следит за mtime и поднимает процесс
  заново. Падение и зависание скрипта рантайм тоже переживает: кадры идут без разметки, процесс
  поднимается заново (упавший — не чаще раза в секунду, зависший — по `stuck_ms`). Скрипт вправе
  рисовать медленно, поэтому «завис» — это когда он молчит дольше `stuck_ms` (по умолчанию 2 с),
  а не когда не уложился в бюджет кадра. Пока скрипт поднимается (импорт `numpy` в обвязке
  и `cv2` в самом скрипте на этой плате занимает секунды), рантайм его не трогает: скрипт сам
  отмечается в разделяемой памяти, что готов к кадрам, и на это ему дается `start_ms`.

Обвязка вызывается так:

```bash
python3 hook_main.py <дескриптор памяти> <размер памяти> <пользовательский скрипт>
```

Раскладка разделяемой памяти описана в
[br_hook_shared.h](./runtime/br_fsm/br_hook/br_hook_shared.h) и продублирована в `hook_main.py`.
Обвязке нужны `python3` и `numpy`: она отдает скрипту кадр готовым массивом под `cv2`.
`cv2` нужен самому скрипту — рисовать чем-то другим тоже можно.
Разделяемая память — POSIX-объект в `/dev/shm`, поэтому он должен быть смонтирован: в образе
из SDK он в `/etc/fstab` есть.

В строке `[fps]` у хука своя колонка — время стадии `hook`.

## Отладка кадров

Под определением `debug_frame` рантайм печатает строку на каждый кадр: времена стадий
(`vi`, `rga`, `npu`, `hook`, `flush`, `venc`, `rtsp`) в миллисекундах и число детекций.
Определение выключено по умолчанию и включается при сборке:

```bash
cmake -S . -B build -DDEBUG_FRAME=ON && cmake --build build && cmake --install build
```
